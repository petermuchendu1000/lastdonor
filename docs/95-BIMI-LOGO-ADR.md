# 95 — The logo in the inbox (BIMI), and what it actually takes

**Date:** 2026-10-21
**Trigger:** owner request — *"add the logo to the favicon (e.g. where
Google shows G, we use our logo)"*

---

## 1. Two different things, one of which is not code

The slot where Gmail shows a letter — the circular sender avatar beside the
subject line — is **not a favicon**. Email clients do not read favicons.
That avatar is **BIMI** (Brand Indicators for Message Identification), and
it is a DNS record plus a certificate, not markup we control.

| | What it is | Status |
|---|---|---|
| Browser tab icon | `src/app/icon.svg` | **Done.** Regenerated from the brand font. |
| Gmail sender avatar | BIMI: DNS + certificate | **Blocked on owner actions.** The logo asset is ready. |

Everything in §4 below is outside this repository and costs money.

---

## 2. What was built

**`public/bimi-logo.svg`** — served at `https://lastdonor.org/bimi-logo.svg`,
which is the URL a BIMI record's `l=` tag points at. Generated by
`scripts/generate-bimi-logo.py`.

### Why generated rather than hand-drawn

The mark is the "LD." lockup in **DM Serif Display**, the face the site and
the email shell already use. A BIMI logo cannot reference a font — the file
is parsed by a mailbox provider with no access to ours, and the profile
forbids external references regardless — so the letters must ship as
outlines. Outlines traced by hand would drift from the brand face, which is
the exact failure `docs/56` records for fonts. The generator pulls real
glyph contours out of `public/fonts/DMSerifDisplay-Regular.ttf`, so the mark
is the brand face by construction.

### The profile is narrow, and failure is silent

BIMI requires **SVG Tiny PS** (`draft-svg-tiny-ps-abrotman-00`). A file that
violates it is not rendered leniently — it is rejected, and the sender keeps
the letter avatar with no error anywhere in the loop. Encoded and pinned by
`src/lib/bimi-logo.ratchet.test.ts` (11 tests, one proven by injecting a
`<text>` element):

- root carries `version="1.2"` and `baseProfile="tiny-ps"` (§2.1)
- exactly one non-empty `<title>`, as a child of `<svg>` (§2.1)
- no `script`, `a`, `image`, `switch`, animation, multimedia or `style` (§2.3)
- no `x`/`y` on the root (§6.2)
- nothing external: no `xlink:href`, no `url(`, and the only URL in the file
  is the SVG namespace itself
- square `viewBox`, outlines only, under 32 KB

### Designed for a circular crop

Gmail crops the avatar to a circle. The background is full bleed so the
crop is solid teal at any radius, and the lockup sits well inside the
inscribed circle. Rendered and checked at 256, 96, 40 and 24px, square and
circular, on light and dark: legible at all of them, with the amber accent
dot fading out gracefully at the smallest size.

**One correction during the work:** the first version centred the *advance
widths* of "LD" and then hung the dot outside that box, which left a wide
gap on the left and almost none on the right. It now centres on measured
ink bounds. Visible immediately in a render, invisible in the source.

### The favicon came along

`src/app/icon.svg` set its letters as `<text>` in **Georgia** — a font the
brand does not use and which is absent on most Linux and Android devices,
so the tab icon fell back to whatever serif happened to be installed and
differed from the email avatar. Both files now come from the same
generator and share the same path data, asserted by the ratchet.

**Then fixed, 2026-10-22 (amendment below):** `src/app/apple-icon.tsx`
had the same fault through a different mechanism. Left out of the first
commit rather than bundled into a change already touching outgoing mail.

## 4. ⛔ What the owner has to do, and what it costs

### Step 1 — collect DMARC reports first (low risk, do this now)

The current record has **no `rua=`**, so nobody is receiving aggregate
reports and nothing is known about what else sends as `lastdonor.org`.
Moving straight to enforcement from that position can silently quarantine
legitimate mail.

```
_dmarc.lastdonor.org  TXT  "v=DMARC1; p=none; rua=mailto:dmarc@lastdonor.org;"
```

Still `p=none`, so nothing changes for delivery. Let it run and read what
arrives.

### Step 2 — move DMARC to enforcement (⚠️ this one can break mail)

BIMI requires enforcement **on the organizational domain and its
subdomains**. Quoting the BIMI Group implementation guide: *"DMARC policy
MUST be at enforcement on the organizational domain and subdomains"*,
accepting `p=quarantine; sp=quarantine` or `p=reject; sp=reject`, and
*"'None' policies or 'pct' less than 100 percent are not accepted."*

```
_dmarc.lastdonor.org  TXT  "v=DMARC1; p=quarantine; sp=quarantine; pct=100; rua=mailto:dmarc@lastdonor.org;"
```

**Do not do this before step 1 has run.** Any sending source that is not
SPF- or DKIM-aligned — a help desk, an invoicing tool, a personal client
sending as the domain — starts getting quarantined the moment this lands.
That is a live deliverability risk and the reason this is an owner
decision, not something to apply from a session.

### Step 3 — obtain a certificate (this is the expensive part)

**Verified from Google's own documentation:** *"to display BIMI logos in
Gmail, you must use a TXT record that refers to a Privacy Enhanced Mail
(PEM) file."* An SVG-only record — which the BIMI spec itself permits, with
`a=` marked optional — **is not sufficient for Gmail**. A certificate is
required, and it is what the PEM contains.

Two kinds exist:

| | Requires | Gmail shows |
|---|---|---|
| **VMC** (Verified Mark Certificate) | a **registered trademark** at an accepted IP office (USPTO, EUIPO, UK IPO, IP Australia and others) | logo **and** the blue checkmark |
| **CMC** (Common Mark Certificate) | **no trademark**; 12 months of prior public use of the logo | logo only, no checkmark |

Issued by DigiCert and Entrust. **Assumed, vendor-sourced and not verified
from a certificate authority's own price list:** roughly **USD 750–1,750
per year**, excluding any trademark registration cost. Treat as an order of
magnitude, not a quote. Google began accepting CMCs on 2024-09-24 according
to the same vendor sources.

For LastDonor, **CMC is the realistic route** — it needs no trademark. The
12-month public-use requirement is worth checking against when the mark was
first published, which this doc cannot establish.

### Step 4 — publish the BIMI record

Once the PEM exists:

```
default._bimi.lastdonor.org  TXT  "v=BIMI1; l=https://lastdonor.org/bimi-logo.svg; a=https://lastdonor.org/bimi-cert.pem;"
```

Google's documentation notes it *"can take up to 48 hours for BIMI to start
working, and for logos to show in recipients' mailboxes."*

---

## 5. Rejected

**Publishing a self-asserted BIMI record now** (`l=` only, no `a=`). It is
valid per the spec and costs nothing, but Google's own page is explicit
that Gmail needs the PEM, and Gmail is the client the request was about.
The BIMI Group's guide says plainly that *"Self-Asserted BIMI records have
limited support across the various Mailbox Providers."* Publishing one
would create the appearance of a finished job while the avatar stayed a
letter. The record is a two-line DNS change whenever a certificate exists;
there is nothing to gain by publishing it early.

**Moving DMARC to enforcement as part of this change.** It is a
prerequisite, it is one DNS edit, and it is the single action here most
likely to cause an outage in mail that currently works. It belongs behind
a monitoring period, which is step 1.

**An `<image>`-based or text-based SVG.** Both are forbidden by the
profile; `<text>` additionally depends on a font the provider does not have.

---

## 6. Honest summary

The logo is ready and will be served at a stable HTTPS URL as soon as this
deploys. The tab icon is fixed and now matches it. **The Gmail avatar will
not change** until DMARC is at enforcement and a VMC or CMC has been
bought — neither of which can be done from here, and one of which carries
real deliverability risk that wants a monitoring period first.

## Amendment, 2026-10-22 — the iOS icon, and why it was the wrong font

`src/app/apple-icon.tsx` asked for `fontFamily: 'Georgia, serif'` and
supplied no font data.

`ImageResponse` renders through **Satori, which has no system fonts at
all** — it draws only with what it is handed. So the request for Georgia
did not fall back to Georgia, or to any serif: it fell through to Satori's
built-in sans. **Verified** by fetching the deployed icon from
`https://lastdonor.org/apple-icon` and looking at it: thin sans-serif
"LD." against the bold serif used by the favicon and the BIMI mark.

Nothing threw and nothing logged. The route answered `200 image/png` the
whole time.

### What changed

- **The real face is embedded.** `public/fonts/DMSerifDisplay-Regular.ttf`
  (72 KB) is read and passed to `ImageResponse` as `fonts`. Naming a
  family is not enough; the bytes have to be supplied.
- **`runtime` is now `nodejs`, not `edge`.** The edge runtime has no
  filesystem, so the font cannot be read there. This is the line that
  would silently undo the fix, which is why a test pins it.
- **The rounded corners are gone.** iOS masks an apple-touch-icon to its
  own squircle. Supplying our own radius cuts a rounded shape out of an
  already rounded one, and the gap between them shows whatever is behind —
  the old version was RGBA with transparent corners, so that gap was
  transparent. Full bleed and opaque is what survives the mask. The
  browser favicon keeps its radius, because nothing masks that one.

### Why the URL did not change

`/apple-icon` is referenced as the `Organization.logo` URL in the JSON-LD
in `src/app/layout.tsx`. A static `app/apple-icon.png` would have been
simpler but serves at `/apple-icon.png`, so it would have 404ed that
structured-data reference or forced an edit to it. Keeping the dynamic
route keeps both the URL and the font in one place. **Rejected:** moving
to a committed PNG, which also risks the binary drifting from the SVG
outlines with nothing to catch it.

### Tested by rendering, not by reading

`src/app/apple-icon.test.tsx` calls the route and inspects the bytes: PNG
signature, 180×180 read out of the IHDR chunk, and `runtime === 'nodejs'`.

The load-bearing one renders the **same markup without the font** and
asserts the two outputs differ. Satori with no font data does not fail, it
substitutes — so "did it render?" proves nothing. If those two ever match,
the embedded font is having no effect, which is precisely the bug that
shipped.

**Verified by injection:** removing the `fonts` option fails the
font-embedding test; switching back to `edge` fails the runtime test. The
file was restored byte-identical after both.
