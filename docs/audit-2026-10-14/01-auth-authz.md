Scope: `src/middleware.ts` default-deny, matcher coverage, IDOR across all 111 API
routes (109 `route.ts` + 2 `route.tsx`), role enforcement, JWT specifics in
`src/lib/auth.ts`, RLS, and the login/register/reset flows. Read-only: no repo file
was modified.

All line references are to the working tree at audit time.

## Controls that already mitigate concerns — do not "fix" these

1. **Default-deny middleware works as designed.** `src/middleware.ts:60-68` matches `/api/:path*` plus `/dashboard`, `/notifications`, `/profile`, `/settings`, `/admin`. My repro script classified all 111 routes: of the 31 middleware-exempt ones, every mutating route except the two in A6 performs its own authentication (`campaign-photos:19`, `campaigns POST:108` `requireAuthRole(['editor','admin'])`, `campaigns/[slug] PUT:81` + owner check, `DELETE:168` `requireRole(['admin'])`, `campaigns/[slug]/messages POST:64` `requireAuth`, both webhooks via signature verification, all 10 cron routes via `verifyCronAuth`).
2. **Every single `/api/v1/admin/**` route checks role.** I enumerated `requireRole([...])` across all 56 admin route files: all present, almost all `['admin']`, a deliberate `['admin','editor']` subset for blog/news-feed/message-moderation/campaign-updates. `/api/v1/upload` is `['admin','editor']`. No admin route relies on the middleware alone, and none reads a role from the request body.
3. **`/admin` pages are role-gated at the layout.** `src/app/admin/layout.tsx:9-14` redirects unless `role` is `editor`/`admin`, with `dynamic = 'force-dynamic'`.
4. **Dashboard pages all re-check ownership server-side.** `dashboard/campaigns/[id]/{page,donors,edit,updates}` compare `campaign.creatorId` to `session.user.id` (allowing editor/admin), and `verification`/`impact-update` go further by filtering the query itself with `eq(campaigns.creatorId, session.user.id)`.
5. **Cron auth is correct.** `src/lib/cron-auth.ts:9-20` length-checks then `timingSafeEqual`s the whole `Bearer <secret>` string; all 10 cron routes call it.
6. **Stripe webhook signature verification** at `donations/webhook/route.ts:28` (`constructEvent`) before any processing, plus in-memory dedup and the schema-level unique index.
7. **No mass assignment.** `updateProfileSchema` (`validators/user.ts:51-58`) and `userPreferencesSchema` (`:60-68`) are narrow allowlists; `users.role` defaults to `'donor'` (`src/db/schema.ts:251`) and is writable only through the admin role endpoint, which is audited (`admin/users/[id]/route.ts:221-233`) and blocks self-demotion (`:188-196`).
8. **Step-up auth on the most dangerous admin route is real.** `admin/settings/environment` PATCH requires a 5-minute HMAC token bound to the admin's user id (`crypto.server.ts:76-108`, constant-time compare), issued only after a bcrypt security-answer check that is itself per-user rate-limited (`admin/settings/verify-security/route.ts:69-77`).
9. **Anonymous-donor redaction and non-owner URL suppression exist.** `api-helpers.ts:redactAnonymousDonor` is applied on the public donors/campaign endpoints, and `user-campaigns/[id]/verification/status/route.ts:70-77` deliberately withholds document `fileUrl`s from non-owners — which is exactly why A2 matters: the code already treats that URL as the secret.
10. **`forgot-password` is enumeration-safe** (`:32-36`, constant response) — the inconsistency is on the login path (A4), not here.
11. **`jwt` callback fails closed** on a DB error: `token.role = 'donor'` (`auth.ts:205-207`).
12. **Cookies are correct**: `httpOnly`, `sameSite: 'lax'`, `secure` in production, `__Secure-`/`__Host-` prefixes (`auth.ts:98-132`).

## Sub-areas where I found nothing

- **IDOR on `[id]`/`[slug]`/`[requestId]` routes.** I swept every dynamic API route for handlers that touch a record without comparing to the session (script in `scratchpad/repro`, then hand-read each). The only hits were public-by-design reads (`blog/[slug]`, `campaigns/[slug]/donors`) and the A6 subscribe route. All of the prioritised routes verify ownership: `user-campaigns/[id]` via `requireOwner` (`:19-56`), `…/updates` (`:45-49`), `…/withdraw` (`:93-98`), `…/withdrawals` (`:41-46`), `…/verification/documents` (`:57-59`), `…/verification/status` (`:46-51`), `…/verification/submit`, `…/impact-update` (`:51-53`, `:119-121`), `info-requests/[requestId]` GET (`:72-78`) and PATCH (`:200-206`), `verification/identity/session` (`:55-57`). Notifications, profile, settings, avatar, balance, subscriptions and all `user/stripe-connect` routes derive the subject solely from `session.user.id` — none accepts a user id from the client (`grep` for `body.userId`/`creatorId: body`/`searchParams.get('userId')` → zero hits).
- **Matcher coverage.** No page outside the matcher needs it: `grep -rln "auth()" src/app --include=page.tsx` outside the matched trees returns only `campaigns/[slug]/congratulations/page.tsx`, which filters its own query by `creatorId = session.user.id` (`:40-46`). There are **no server actions** in the repo (`grep -rn "use server" src` → no hits), so there is no unprotected action surface.
- **Role bypass via client-supplied fields.** None found; `VALID_ROLES` is validated against `userRoleEnum` and roles are never read from a request body outside the admin endpoint.
- **Session cookie flags / CSRF cookie naming.** Correct; nothing to report.
