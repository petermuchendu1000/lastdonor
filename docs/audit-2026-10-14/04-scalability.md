# 04 — Scalability & Performance Audit

**Scope:** query performance, unbounded reads, N+1, pagination, caching correctness, payload/bundle, connection usage, serial external calls.
**Target failure mode:** a single campaign goes viral.

**Method / limits of certainty.** No live database, therefore **no `EXPLAIN` was possible**. Index claims were verified by reading `src/db/schema.ts` *and* every `CREATE INDEX` statement in `src/db/migrations/*.sql` (127 statements extracted; 75 distinct declared in schema). Where a statement is about planner *behaviour* rather than index *existence*, it is labelled PLAUSIBLE. Row-count growth conditions are derived from the write paths that insert into each table, which is checkable without a DB.

**Cross-check against `docs/26`.** Three of its "verified properties" do not hold against the code as written and are corrected below: §5 Layer 3 ("echo columns already avoid the N+1 listing queries" — the echo columns are never written: SCAL-06), §9 ("a page with `revalidate = 60` costs the origin ~1 render per 60s *globally*" — defeated per-donation by `revalidatePath`: SCAL-01), and §1 ("ISR surface 26 pages" — 12 of them are admin pages that call `auth()` and 1 is `/campaigns` which reads `searchParams`, so they render dynamically: SCAL-12, SCAL-19).

## Sub-areas examined with no findings, and existing mitigations that work

These are recorded so the absence of a finding is not mistaken for an absence of review.

- **Transactions holding external I/O (scope item 7): clean.** All 17 non-test `db.transaction` call sites were read. **None** awaits Stripe, Resend, or an AI call inside the transaction. `payment-service.ts:88-205` is pure DB. The bulk-refund path explicitly splits Stripe I/O (phase 1) from persistence (phase 2) with a comment saying why (`cancel/route.ts:202-203`). `stripe-connect/webhook/route.ts:137-152` and `:200-215` close the transaction before the notification lookups at `:156-179`. The pool-exhaustion risk in this codebase is **concurrency breadth, not transaction duration**: SCAL-01 (6 queries per campaign render, now once per donation instead of once per 60s), SCAL-15 (~2,100 serial statements per cron run on the same pool), and SCAL-08's unbounded fire-and-forget fan-out. Worst case, quantified: `max: 5` per instance × 2 machines = 10 server-side connections (`docs/26 §6`); one campaign-page render requests 5 concurrently (`campaigns/[slug]/page.tsx:245-251`), so **two concurrent cold renders saturate a single instance's pool** and a third queues behind `connect_timeout: 10`. With SCAL-01 making cold renders the norm during a donation spike, that is reachable.
- **Max page-size cap (scope item 4): present and correct.** `MAX_LIMIT = 50` (`api-helpers.ts:31`) with `Math.min(Math.max(1, ...), maxLimit)` at `:45`. `?limit=100000` yields 50. `notifications/route.ts:18` raises it to 100 deliberately; `audit-log/route.ts:31` caps at 200 independently. No uncapped `limit` was found. The gap is `offset` only (SCAL-13).
- **Stripe webhooks are exempt from rate limiting.** `rate-limit.ts:185` (`if (pathname.includes('/webhook')) return null;`) runs before the Upstash call. Without it the `donations` tier — `slidingWindow(10, '60 s')` keyed by IP (`:72-77`, `:187-189`) — would 429 Stripe's webhook sender above 10 donations/minute, which is precisely the viral case. This is correct and should not be refactored away.
- **`create-checkout` write path is clean.** `donations/create-checkout/route.ts:42-59` is a single projected query, and the connection is released before the Stripe call at `:76`. One DB round trip, one external call, no transaction.
- **OG image fonts are memoized.** `src/lib/og-fonts.ts:11-28` caches both font buffers in module scope, so `/api/v1/og/campaign/[slug]` does not re-read from disk per request — relevant because social-share traffic hits this hard during a spike. The route is also projected (`og/campaign/[slug]/route.tsx:26-33`) and gets `s-maxage=86400` from `next.config.ts:144-150`.
- **`recharts` is kept off public first load** via `next/dynamic` in the only two consumers (`admin/monitoring/page.tsx:3`, `admin/reports/page.tsx:6`).
- **Public column projection is disciplined.** `src/db/public-select.ts` exists and is used by the campaign detail page and APIs, so the 50-column `campaigns` table is not returned wholesale on public paths. The bare `db.select()` instances are confined to the webhook, crons, and admin/dashboard paths (SCAL-18, SCAL-15, SCAL-16, SCAL-22).
- **`resolveDonorNames` is already de-N+1'd.** `notifications.ts:391-424` batch-resolves names with two `inArray` queries instead of one lookup per recipient. It is cited under SCAL-04 only because its second query (`:409-412`) filters on the unindexed `donations.donor_email`; the batching itself is right.
- **No cross-user ISR cache leak found.** Every page declaring `revalidate` was checked for `cookies()`/`headers()`/`auth()`. The 12 matches are all under `/admin`, all call `auth()` (which forces dynamic rendering), and all sit under a `force-dynamic` layout. No public ISR page reads per-user state. SCAL-19 records the dead config and the latent risk, not a live leak.
- **`/search` is a redirect**, not a query path (`src/app/search/page.tsx:9-11`), so there is nothing to audit there; the real search is `/api/v1/search` (covered in SCAL-12) and `/campaigns`.
- **Donation idempotency is intact.** `uniqueIndex` on `donations.stripe_payment_id` exists in both schema (`:385`) and migrations (`0015_user_campaigns.sql:49`), and `onConflictDoNothing` at `payment-service.ts:103` relies on it. Replayed webhooks remain no-ops.
