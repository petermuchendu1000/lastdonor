# 34 — Migration Baseline (ADR), 2026-10-14

Supersedes the migration-repair plan in `docs/31` §1.1, which was based on an
incomplete diagnosis. Resolves the ⛔ hazard recorded in `CLAUDE.md` and
`docs/29` §2.

---

## 1. The problem, fully diagnosed

`docs/29` §2 established that `meta/_journal.json` held 9 entries against 33
`.sql` files, and that `drizzle-orm`'s migrator iterates **only**
`journal.entries` (`migrator.js:12`, verified). It then prescribed: repair the
journal and apply all 33 onto the empty database.

**That prescription was wrong, and would have failed mid-deploy.** The directory
contains **two overlapping lineages that cannot be replayed together**:

| Lineage | Contents | Creates |
|---|---|---|
| **Journaled** — 9 codename-style files, `0000_square_chronomancer` … `0008_add-veriff-session-fields` | `0007_smart_tusk.sql` is a **late regenerated baseline** | `notification_type`, `verification_status`, `withdrawal_status`, `blog_source`, `blog_topic_status`, `milestone_status`, `fund_release_status`, `info_request_status`, `support_channel`, `document_status`, `refund_batch_status`, `refund_record_status`, `bulk_email_status`, `support_conversation_status`, `support_priority` |
| **Unjournaled** — 24 descriptive-name files, `0007_add_notifications` onward | `0015_user_campaigns.sql`, `0018_blog_pipeline.sql`, `0019_trust_verification.sql`, `0022_stripe_connect_payout.sql` | **the same types again** |

**Verified, not inferred.** A dry run of all 33 concatenated, inside a
transaction, against the live database on 2026-10-14 failed at:

```
ERROR: 42710: type "notification_type" already exists
```

The same database was independently confirmed to hold **zero** enums in
`public`, so the collision is between two migrations in the set, not with
pre-existing state. Replay in filename order is impossible by construction.

**A second, independent defect:** `0027_oblique_audit_enforcement.sql` adds
`CHECK (failed_login_count >= 0)` for a column **no migration creates**
(`schema.ts:270` declares it). It fails with `42703`, and because Drizzle runs
pending migrations in a single transaction it takes down 0027's other 10 CHECK
constraints — including `campaigns_released_lte_raised`, which `docs/29` P0-3
depends on — plus 3 blog foreign keys and the donation trigger.

---

## 2. Decision

**Generate one baseline from `schema.ts` and make it the only migration path.**

- `src/db/migrations-v2/0000_cheerful_robbie_robertson.sql` — 659 statements,
  31 `CREATE TABLE`, generated by `drizzle-kit generate` from `schema.ts`.
- `drizzle.config.ts` `out` now points at `./src/db/migrations-v2`.
- The 33 original files **stay on disk, untouched**, with a `README.md`
  explaining their status. They are inert because the migrator reads only the
  journal of the directory `out` names.

**Validated before adoption.** The baseline was run against the live database
inside `BEGIN … ROLLBACK`: every statement accepted, nothing committed. This is
the only migration artifact in the project's history that has been proven to
apply.

**Why `schema.ts` is a safe source of truth here, when `CLAUDE.md` says not to
trust it as a description of production:** that warning exists because the live
schema was unknowable. It is now known — the database is **empty** (0 tables, 0
enums, 0 `auth.users`, no `drizzle.__drizzle_migrations`; `docs/33` §1). With no
existing rows and no existing schema, the desired end state *is* `schema.ts`,
and the historical path to it is irrelevant.

---

## 3. Rejected alternatives

**Repair the journal and replay all 33.** The original `docs/31` §1.1 plan.
Rejected: impossible, per §1. Reconciling the two lineages by hand would mean
editing ~24 historical migrations to make them idempotent against each other —
high-risk work whose only output is a schema we can generate correctly in one
command.

**Fold the lineages into a corrected linear history.** Rejected: it buys
genuine migration history, which matters when you must preserve data. There is
no data. The cost is days of careful work and a large surface for exactly the
class of defect being fixed.

**`drizzle-kit push`** (what CI uses for integration tests). Rejected as the
mechanism of record: it diffs `schema.ts` against the live database and applies
without leaving a migration artifact, so there is nothing to review, version or
replay. Correct for ephemeral test databases, wrong for production.

**Delete or archive the 33 files.** Rejected: destructive, and unnecessary —
they are already inert. Keeping them preserves the audit trail behind `docs/29`
and this document, and keeps the change fully reversible by `git revert`.
`0027` is deliberately left unpatched: it is now historical, and editing a
superseded migration would imply it is still live.

---

## 4. Trade-offs accepted

- **Migration history before 2026-10-14 is not replayable.** Acceptable: it was
  never replayable, which is the finding. The history is preserved as documents,
  not as an executable path.
- **Two migration directories exist**, which is confusing until the old one is
  removed. Mitigated by the `README.md` and this ADR. Removal is a separate,
  owner-approved cleanup.
- **The baseline has not yet been applied to any database.** It is validated but
  not committed to production — see §5.

---

## 5. Application path

The schema is applied by **Fly's `release_command`** running `drizzle-kit
migrate` over **port 5432 (session mode)**, per `docs/26` §6 and §10 step 4.
Transaction mode on 6543 cannot hold the session state that DDL and advisory
locks need.

This was chosen over applying it from a developer session: the deploy host
reaches Postgres directly, the apply is reproducible and versioned, and it runs
through the mechanism the architecture already specifies. Two attempts to apply
it from this session were correctly refused by the environment's safety
controls as a production schema write; the designed mechanism is the better
answer regardless.

**On first deploy, the `release_command` creates the entire schema.** That is
expected, and it is why the baseline was dry-run first.

---

## 6. Consequences

- `npm run db:migrate` is **safe again** and applies exactly the baseline. The
  ⛔ in `CLAUDE.md` is lifted.
- `npm run db:generate` is **safe again**: it now diffs against the baseline's
  own snapshot rather than the stale `0008` snapshot, so it emits a correct
  incremental migration.
- Future schema changes follow the normal flow: edit `schema.ts`, run
  `db:generate`, review the emitted SQL, commit, deploy.
- `docs/31` §1.1 is superseded by this document.
- `docs/29` §2's flip-table is fully resolved: the database is empty, so every
  row resolves to "not applied", and the baseline creates all of it — including
  the unique index on `donations.stripe_payment_id` that `CLAUDE.md` flags as
  the only replay protection, which `schema.ts:385` declares as `uniqueIndex`.
